# Paperclip architecture notes for ion's operations workspace

Researched 2026-09-30 against first-party Paperclip documentation, source, and release notes. This note adds architecture details to [the earlier Paperclip product research](RESEARCH-PAPERCLIP.md); it is not a claim that every documented surface is enabled in every Paperclip build. **Confirmed** below means documented in current first-party source or docs. **Proposal for ion** is a design inference, not Paperclip behavior.

## Architectural backbone

**Confirmed.** Paperclip describes itself as a company-scoped control plane: React UI → Express REST services → PostgreSQL/Drizzle, with adapters that invoke external agent runtimes. A heartbeat enters a DB-backed execution flow, invokes an adapter, lets the agent use the task API, then records logs, usage, cost, and resumable session state. Agents and the UI use the same API. Tasks (issues) have one assignee and atomic checkout. [Architecture](https://github.com/paperclipai/paperclip/blob/master/docs/start/architecture.md), [core concepts](https://github.com/paperclipai/paperclip/blob/master/docs/start/core-concepts.md), [Paperclip repository overview](https://github.com/paperclipai/paperclip).

**Proposal for ion.** Build a shared operations data model around `project → task → run`, with independent `agent`, `decision`, `notification`, `routine`, `workflow`, `artifact`, and `usage event` records referencing those IDs. Each navigation view is a projection of this model, not its own task database. Where Paperclip uses `companyId`, ion needs a clearly defined workspace/account boundary so an “across projects” query cannot accidentally become an across-user or across-tenant query.

## Surface-by-surface evidence and transfer

| User surface | Confirmed Paperclip behavior / source | Proposal for ion |
| --- | --- | --- |
| **Dashboard** | Dashboard aggregates live agents, work counts, spend/budget, approvals and activity; entities remain separate and are linked into detail views. Paperclip's architecture and repository overview describe runs, activity, costs, and tasks as distinct records. [Dashboard guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/dashboard.md), [architecture](https://github.com/paperclipai/paperclip/blob/master/docs/start/architecture.md) | Make the landing page a compact cross-project read model: active agents/runs, tasks by state, blocked work, decisions due, spend, and latest artifact. Every count needs a drill-down using the same filter and scope. |
| **Decisions** | Formal approvals, issue interactions, run recovery, blocked work, and agent-proposed decisions can appear as heterogeneous attention sources. The Decisions desk stores queue membership and triage as sidecars keyed by `(source_kind, source_id)`, resolves each source for authorization at read time, and records append-only triage history. [Decisions guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/decisions.md), [database notes](https://github.com/paperclipai/paperclip/blob/master/doc/DATABASE.md) | Define a common `attention item` envelope with source ID/type, project, responsible user, urgency, due time, options, effect preview, and resolution. Keep canonical approval/review records in their owning domain. Aggregate actionable items across projects and derive dashboard badges from the same query. |
| **Teams / agent creation** | Agents have role, capabilities, reporting line, adapter/model, status, budget, instructions, skills, and run history. Instructions can be managed or external bundles and take effect on the next heartbeat; optional company skills are attached per agent. Team Catalog previews imports of agents, reporting links, projects, tasks, routines, and skills. [Agents guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/org/agents.md), [Team Catalog](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/org/team-catalog.md) | Make Teams the primary creation flow: role/expertise, instructions, runtime/model, resource scope, app access, budget, reporting/delegation, and a test run. Offer a reviewable template preview. Treat the org chart as one visualization of assignment/delegation policy, not the whole team feature. |
| **Team delegation** | Managers create child issues with parent/goal links; cross-team assignment is possible; agents cannot assign to paused agents or create delegation cycles. Atomic checkout prevents duplicate concurrent work. [Delegation guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/org/delegation.md), [heartbeat protocol](https://github.com/paperclipai/paperclip/blob/master/docs/guides/agent-developer/heartbeat-protocol.md) | Store explicit parent/child and dependency edges, assignee, delegation provenance, and acceptance/checkout. Enforce cycle and paused-agent guards in the coordinator, not just instructions. Show handoffs and parallel branches at the project/task level. |
| **App and resource access** | Current Paperclip release describes Apps and a connector catalog, connection grants, delegated identities, and agent connection requests in task feeds. First-party connector playbook specifies a run-scoped gateway capability; the agent does not receive a durable vendor credential. Gateway rechecks connection, grant, policy and run context per call; secrets remain server-side with audit evidence. Its current default is permissive for discovered actions, so a narrower ion default would be an intentional product choice. [v2026.916.0 release](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.916.0.md), [connector playbook](https://github.com/paperclipai/paperclip/blob/master/doc/connections/CONNECTOR-PLAYBOOK.md) | Give users a visible agent × app/resource access matrix, with identity owner, allowed actions, project scope and revocation. Route agent app calls through a policy-checking gateway with run-scoped credentials. Do not encode permission only in prompt text. |
| **Inbox** | Inbox has Mine, Recent, Unread, Blocked, All. A blocked issue records a concrete unblock reason and owner; human-owned blocks enter an attention feed, while agent-owned ones wake the agent. Inbox archive/read state is presentation state distinct from issue status and assignment. [Blocked Inbox](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/blocked-inbox.md), [implementation spec](https://github.com/paperclipai/paperclip/blob/master/doc/SPEC-implementation.md) | Use Inbox for notifications and follow-up events: done, failed, blocked, mentioned, review needed, artifact ready. Keep unread/archive per user. Route calls for human judgment into Decisions while retaining the event in Inbox history. Every failure/blocked item should name the owner and next action. |
| **Routines** | A routine is a recurring work definition; cron/webhook/API/manual triggers create regular execution issues. Concurrency (`coalesce`, enqueue, skip) and missed-run policies are explicit, with run history. [Routine reference](https://github.com/paperclipai/paperclip/blob/master/skills-releases/paperclip/v0/references/routines.md) | Store routine definitions and generated run/task instances separately. A schedule should specify owner agent/team, project, prompt, timezone, concurrency, catch-up, and failure routing. Generated tasks should obey ordinary budget, permissions, audit and artifact rules. |
| **Workflows / Pipelines** | Paperclip now has pipeline primitives, evidenced by its first-party CLI/API tutorial: stage definitions, allowed transitions, case instances with version numbers, review gates, child rollups, blockers, suggested transitions, routine automation, issue links, and event history. Stale case writes return `409 version_conflict`. The tutorial explicitly calls some template behavior a convention rather than a built-in primitive. The sidebar shows Pipelines conditionally (`showPipelines`), so tutorial capability does not prove every deployed UI has the same editor. [Pipeline tutorial](https://github.com/paperclipai/paperclip/blob/master/docs/pipelines-tutorial.md), [sidebar source](https://github.com/paperclipai/paperclip/blob/master/ui/src/components/Sidebar.tsx), [issue-route case links](https://github.com/paperclipai/paperclip/blob/master/server/src/routes/issues.ts) | Bind a versioned workflow definition to a project. A workflow run has stage instances, participants, artifacts, guard results, and transition events; tasks remain the executable work. Start with linear release/deployment templates, explicit human review gates and retryable stage actions. Add branching only once the simple model is reliable. |
| **Artifacts** | Paperclip introduced a company-scoped Artifacts page that indexes work products across issues/runs. Artifact deliverables are uploaded attachments plus a work-product record; a `workspace_file` reference is a signpost, not a durable upload. Attachment-backed artifacts remain accessible after a workspace is removed. [v2026.609.0 release](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.609.0.md), [agent artifact contract](https://github.com/paperclipai/paperclip/blob/master/doc/AGENT-ARTIFACTS.md) | Index artifact metadata across projects with project/task/run/agent provenance, content type, version and storage state. Distinguish durable uploaded deliverables from local workspace links. Support preview and direct return to the producing work. |
| **Usage & costs** | Paperclip records cost events with agent, task/project/goal, provider/model, tokens and cost, then rolls them up. Costs UI separates agent/project, provider/model, and biller views; budget hard stops can pause agents. A September 2026 open bug report says Codex ACP may undercount multi-request runs and leave some usage unpriced; this is a report, not verified current behavior here. [Implementation spec](https://github.com/paperclipai/paperclip/blob/master/doc/SPEC-implementation.md), [Costs guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/costs.md), [reported bug #14003](https://github.com/paperclipai/paperclip/issues/14003) | Name the surface **Usage & Costs**. Keep an append-only usage ledger linked to run, agent, project, provider, model and biller; distinguish measured, estimated, subscription-covered and unpriced usage. Reconcile adapter totals before enforcing a money limit. Retain an Activity/Run Timeline separately for “what happened when.” |

## Boundaries to preserve in the plan

1. **Operations vs execution.** Paperclip's UI/server orchestrate runtimes through adapters, and agents work through the API. ion can use a native client, but scheduling, authority and durable state still need one coordinator; view code should never infer work state from transient process UI. [Architecture](https://github.com/paperclipai/paperclip/blob/master/docs/start/architecture.md), [execution semantics](https://github.com/paperclipai/paperclip/blob/master/doc/execution-semantics.md).
2. **Project scope vs account scope.** Paperclip is explicitly company-scoped, including strict company checks in its route/service conventions. The requested “across projects” views should query one authorized workspace/account and preserve project filters, not flatten separate trust domains. [Architecture](https://github.com/paperclipai/paperclip/blob/master/docs/start/architecture.md), [Paperclip AGENTS.md](https://github.com/paperclipai/paperclip/blob/master/AGENTS.md).
3. **Actionable queue vs event feed.** Paperclip's Decisions desk uses source identities and source authorization; its Inbox can retain presentation state without changing work. This supports separate but connected Decisions and Inbox screens. [Database notes](https://github.com/paperclipai/paperclip/blob/master/doc/DATABASE.md), [implementation spec](https://github.com/paperclipai/paperclip/blob/master/doc/SPEC-implementation.md).
4. **Workflow case vs task execution.** Current Paperclip pipelines add a case/stage model and link cases to ordinary issues. For deployment/release workflows, ion should likewise keep definition, workflow run, stage run, task run and artifact IDs distinct. The tutorial's template conventions are evidence to avoid promising a full no-code DAG engine in the first release. [Pipeline tutorial](https://github.com/paperclipai/paperclip/blob/master/docs/pipelines-tutorial.md), [issue-route case links](https://github.com/paperclipai/paperclip/blob/master/server/src/routes/issues.ts).
