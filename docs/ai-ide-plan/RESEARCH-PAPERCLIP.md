# Paperclip research: agent company flow, interface, and automation

Researched 2026-09-29 from the first-party [Paperclip repository](https://github.com/paperclipai/paperclip), [documentation source](https://github.com/paperclipai/paperclip-docs), and [releases](https://github.com/paperclipai/paperclip/releases). This is a source note for ion product planning, not an implementation specification. Paperclip changes rapidly; where docs, implementation, release notes, and open issues disagree, the distinction is called out below. No Paperclip instance was installed or operated for this review, so the UI observations are from first-party docs and current source, not hands-on screenshots.

## Product model and end-to-end journey

Paperclip is a management/control layer over externally powered agent runtimes. An organization contains goals, agents, projects, issues, budgets, approvals, and run history. Agents have an adapter, role, reporting line, capabilities, budget, and status. Work is represented by issues, which can be nested and linked to projects and goals. The org tree defines managerial responsibility and escalation, while tasks can be assigned across teams. [Core concepts](https://github.com/paperclipai/paperclip/blob/master/docs/start/core-concepts.md), [org structure](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/org/org-structure.md), [issues API](https://github.com/paperclipai/paperclip/blob/master/docs/api/issues.md).

The documented human journey is:

1. Install/open Paperclip and enter the onboarding wizard. Current docs describe a three-screen card: name the organization, hire the first agent, connect a model. The organization is created after its name; the goal is added afterwards from Goals. This supersedes older repo guidance that put the goal immediately in company creation. [Current company guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/getting-started/your-first-company.md), [older company guide](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/creating-a-company.md).
2. Create/connect the first agent. The older first-agent guide says it is automatically a CEO with adapter, model, working directory, credentials, and heartbeat interval, plus a disabled initial heartbeat and separate Budget tab. The August 31 release **changed onboarding**: the agent step now asks for a name only and the onboarding hire starts as `general`; the September 16 release describes a connected first agent/chat rather than the older CEO-first setup. Thus the older guide describes a supported organizational pattern, **not a reliable description of the latest default wizard**. [First-agent guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/getting-started/your-first-agent.md), [v2026.831.0 release](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.831.0.md), [v2026.916.0 release](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.916.0.md).
3. Add a concrete, measurable goal, then direct the first agent through the chat-first task. In the **documented CEO-led workflow**, a CEO reads the goal and proposes a strategy on its first heartbeat. The proposal normally includes interpretation, projects/focus areas, initial tasks, and team shape; the human approves, rejects, or requests revisions. The 2026.824 and 2026.916 releases describe newer onboarding where the wizard ends inside a task conversation; a chief-of-staff agent greets the user, asks clarifying questions, and proposes a plan approved item by item. Do not assume the older CEO strategy approval is the exact latest first-run UI. The useful durable principle is a human review gate before autonomous plan execution. [Company guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/getting-started/your-first-company.md), [watching agents work](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/getting-started/watching-agents-work.md), [v2026.824.0 release](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.824.0.md), [v2026.916.0 release](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.916.0.md).
4. After approval, the CEO creates issues and can assign/delegate based on roles. With only a CEO, it does the work itself. Agents may propose hires, which go to a human approval queue with proposed role, capabilities, adapter configuration, reporting line, and budget. A human can also hire directly. [Watching agents work](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/getting-started/watching-agents-work.md), [delegation guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/org/delegation.md), [agents guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/org/agents.md).
5. The user supervises from Dashboard, Decisions, Inbox/Blocked, Issues, Agent Runs, Activity, Costs/Budgets, and the work timeline. They can assign a task directly, comment/mention an agent, pause an agent, run a heartbeat manually, change a goal, or change budgets. [Dashboard guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/dashboard.md), [decisions guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/decisions.md), [issues guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/issues.md), [work timeline](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/work-timeline.md).

### The automation loop

A heartbeat is a bounded agent execution, not a continuously running agent. Documented triggers include schedule, new assignment, mention/comment, manual invoke, and approval resolution. The adapter invokes the configured runtime, gives it a short-lived run credential and contextual variables (`PAPERCLIP_TASK_ID`, wake reason, approval id/status), then captures transcript, output, usage/cost, and session state for the run record. Session state may persist across heartbeats. [Core concepts](https://github.com/paperclipai/paperclip/blob/master/docs/start/core-concepts.md), [how agents work](https://github.com/paperclipai/paperclip/blob/master/docs/guides/agent-developer/how-agents-work.md), [authentication](https://github.com/paperclipai/paperclip/blob/master/docs/api/authentication.md).

The protocol asks agents to check identity and any resolved approval, read their priority-sorted assignments, continue active work, then claim a new issue with atomic checkout. Checkout rejects a competing agent with `409`; agents should not retry that issue. They update the issue with progress comments, finish as done/review, or explicitly block and explain. Managers delegate with child issues carrying `parentId` and preferably `goalId`. A run id accompanies state mutations so audit can attribute changes. [Heartbeat protocol](https://github.com/paperclipai/paperclip/blob/master/docs/guides/agent-developer/heartbeat-protocol.md), [issues guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/issues.md), [issues API](https://github.com/paperclipai/paperclip/blob/master/docs/api/issues.md).

Delegation has hard guards: agents cannot assign work to paused agents and cannot create a child task that loops back to the creator of a still-open ancestor. The latter returns `delegation_cycle`. Humans retain reassignment power. This prevents quiet stalls and infinite delegation loops without relying only on prompting. [Delegation guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/org/delegation.md).

### Routine automation

A routine is a recurring definition tied to an agent and project. Each firing creates an ordinary execution issue, so scheduled work enters the same assignment, budget, issue, and audit pipeline. Triggers can be five-field cron with IANA timezone, signed webhook, or API/manual. There are explicit concurrency choices (`coalesce_if_active`, `always_enqueue`, `skip_if_active`) and catch-up choices (`skip_missed`, `enqueue_missed_with_cap`), plus active/paused/archived lifecycle, run history, and optional idempotency keys for manual runs. [Routine reference](https://github.com/paperclipai/paperclip/blob/master/skills-releases/paperclip/v0/references/routines.md), [shared constants](https://github.com/paperclipai/paperclip/blob/master/packages/shared/src/constants.ts).

An older reported bug in version 2026.325.0 says `skip_missed` fired overdue routines on startup. This is a historical user report, not proof that current versions retain it; it is a useful reminder to test restart/catch-up semantics. [Issue #3108](https://github.com/paperclipai/paperclip/issues/3108).

### Team templates

Paperclip's Team Catalog packages agents, reporting lines, projects, tasks, routines, and skills. Users browse bundled or optional teams; select a template; preview the exact import without mutation; choose the reporting attachment point and runtime per agent; opt in to external skills and provide needed secrets; then install. Catalog entries include executive, product engineering, product design, and optional content examples. This solves the blank-page setup problem while making the configuration reviewable. [Team Catalog guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/org/team-catalog.md), [CLI team commands](https://github.com/paperclipai/paperclip/blob/master/doc/CLI.md).

## Governance and human decisions

Formal approvals cover agent hires, CEO strategy, and budget overrides. An approval has requester, type, payload, linked issues, comments, status, and decision note. The normal lifecycle is `pending → approved | rejected | revision_requested → resubmitted → pending`. Hire details summarize the proposed agent and expose a raw payload expander. Strategy details render the plan as markdown and link draft issues. The human can pause/resume/terminate agents and reassign work independently of approvals. [Approvals guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/approvals.md), [approvals API](https://github.com/paperclipai/paperclip/blob/master/docs/api/approvals.md).

The newer Decisions page is meant to gather approval requests, questions, join requests, recoveries, blocked chains, reviews, failed runs, budget alerts, and agent proposed decisions in one ranked human-action queue. For a proposed decision, an agent specifies a question, explanation, and up to eight options with concrete effects (comment, create issue, status/assignee/blocker change, cancellation). Options may request up to four human input fields. Paperclip snapshots affected issue state at proposal time and disables stale options, asks for typed confirmation for destructive tree cancellation, treats `Dismiss — no effects` as an explicit no, expires unanswered proposals by default, and shows recent decided/expired items. [Decisions guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/decisions.md), [current decision route/source](https://github.com/paperclipai/paperclip/blob/master/ui/src/pages/DecisionQueuePage.tsx).

**Important observed limitation:** older first-party issue reports describe formal approvals that existed in the API but were absent from primary navigation in 2026.403/416. Later docs and routes clearly add Approvals and Decisions, but a later report (#9679, July 2026) found a dashboard `Pending Approvals` count of zero while `request_confirmation` cards accumulated in issue threads. The report attributes the count to formal approval rows only. Its status is an open issue in the inspected source; this research did not verify whether a still newer release fully fixes the metric. For ion, a single human-action count must include every actionable mechanism, with a direct route to the exact item and no false zero. [Issue #3821](https://github.com/paperclipai/paperclip/issues/3821), [issue #4254](https://github.com/paperclipai/paperclip/issues/4254), [issue #9679](https://github.com/paperclipai/paperclip/issues/9679), [current routes](https://github.com/paperclipai/paperclip/blob/master/ui/src/App.tsx).

Execution policy is a separate per-issue review/approval mechanism: a runtime-required progress comment, optional reviewer, optional approver, and stage transitions after executor completion. Do not conflate these stage approvals, strategy/hire approvals, and issue-thread confirmation cards just because each asks a human for input. [Execution policy guide](https://github.com/paperclipai/paperclip/blob/master/docs/guides/execution-policy.md), [issues guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/issues.md).

### UX patterns with clear transfer value to ion

These are *inferences for ion*, grounded in the cited Paperclip behavior:

1. **Outcome first, operations second.** Start with a concrete objective and a preflighted team proposal; let the user inspect the planned work, agents, workspace, budget, and decision gates before autonomous execution. Paperclip's goal → CEO strategy approval → issue tree makes the relationship visible. [Company guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/getting-started/your-first-company.md), [watching agents work](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/getting-started/watching-agents-work.md).
2. **One work object for all triggers.** Scheduled routines, direct assignments, and delegated work all become issues with owner, status, comments, and audit. A user should be able to ask “what ran overnight?” from one timeline without knowing the trigger mechanism. [Routine reference](https://github.com/paperclipai/paperclip/blob/master/skills-releases/paperclip/v0/references/routines.md), [work timeline](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/work-timeline.md).
3. **One actionable human queue with effect previews.** The useful layer is broader than yes/no approvals: unanswered questions, stale plans, budget stops, failed runs, blocker chains, and review gates. Each row needs owner, reason, age, affected targets, exact outcome, and an immediate route to context. Paperclip's Decisions flow offers state snapshots and stale-choice disablement; its reported count mismatch shows why ion must derive every badge from the same canonical actionable set. [Decisions guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/decisions.md), [issue #9679](https://github.com/paperclipai/paperclip/issues/9679).
4. **Make team setup inspectable.** A preview that states which agents, routines, skills, credentials, projects, and reporting links will be installed is more trustworthy than a hidden preset. [Team Catalog](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/org/team-catalog.md).
5. **Show coordination, not just transcripts.** Individual runs explain what one agent did; issue trees and a shared timeline explain the handoffs and concurrent work. [Timeline guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/work-timeline.md), [issues guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/issues.md).

## Runtime and execution boundaries relevant to ion

Paperclip's local adapters run on the Paperclip host by default. Its experimental Environments feature can choose a named local, SSH, or plugin-provided sandbox target with instance default and per-agent/project overrides; a sandbox can have a prepared reusable image. Its isolated-workspace project controls govern per-task checkout/workspace behavior. This is explicit routing, not evidence that every Paperclip agent automatically has safe host/sandbox parity. [Environments guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/experimental/environments.md), [project CLI](https://github.com/paperclipai/paperclip-docs/blob/main/docs/reference/cli/project.md).

Paperclip's run credential is a short-lived JWT scoped to agent/run; long-lived keys exist for external agents. The default local trusted deployment mode treats requests as a board operator with no login, while authenticated mode has board sessions and company scoping. This matters when translating the idea into ion's personal desktop/cloud architecture: a remote worker must not inherit the user's full local desktop or model credentials merely because it participates in a team. [Auth docs](https://github.com/paperclipai/paperclip/blob/master/docs/api/authentication.md), [how agents work](https://github.com/paperclipai/paperclip/blob/master/docs/guides/agent-developer/how-agents-work.md).

## Maturity and source caveats

- The 2026.824 release made chat-style tasks the default and a chat-first onboarding landing, while some current docs still call the chat task view experimental. The 2026.831 release changed onboarding hires from the older CEO-first guide to a minimal `general` agent step. Use release notes/current source for default UI, and docs for detailed interaction patterns that may still exist in classic/CEO-led workflows. [v2026.824.0](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.824.0.md), [v2026.831.0](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.831.0.md), [issues guide](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/issues.md).
- The Decisions doc still points to a Training library, but v2026.824.0 release notes explicitly removed its UI route, row actions, and drawer. It should not be used as a current UI precedent without inspecting the installed version. [Decisions doc](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/decisions.md), [v2026.824.0 release](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.824.0.md).
- The older `doc/SPEC.md` marks heartbeat and UI sections **DRAFT**; it is useful design context but not proof of shipped behavior. Current product claims above rely on user guides, APIs, UI routes, and release notes. [Draft spec](https://github.com/paperclipai/paperclip/blob/master/doc/SPEC.md).
- Decisions, formal approvals, issue-thread confirmations, and execution-policy stages are distinct in source/docs. The reported dashboard mismatch is evidence to avoid claiming one perfectly unified approval surface. [Decisions](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/decisions.md), [approvals](https://github.com/paperclipai/paperclip-docs/blob/main/docs/guides/day-to-day/approvals.md), [issue #9679](https://github.com/paperclipai/paperclip/issues/9679).
- No live Paperclip deployment, mobile session, accessibility audit, or quantitative performance test was run for this note. The table above is documentation/source-backed UI description, not visual QA.
