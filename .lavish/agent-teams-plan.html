Who delegates to whom?

A member delegates to direct reports. Reporting lines govern authority; assignment dependencies govern when work can begin. Role names below are examples.

flowchart TD
  User["You · outcome, access, budget"] --> Lead["Team lead · plan and final result"]
  Lead --> Research["Researcher · evidence"]
  Lead --> Manager["Engineering manager · implementation"]
  Manager --> Engineer["Engineer · patch and checks"]
  Manager --> Reviewer["Reviewer · findings and acceptance"]

Each agent, including the lead, has its own harness and model choice. For example: Nebius lead, Codex engineer, Claude reviewer. Environment is a separate Local / Nebius sandbox choice. An agent may belong to several teams; each task pins the selected team's hierarchy and instructions.

Choose a team and project

  • Live assignments: current task, status, actual environment, fallback reason, result and blocker.

Your attention

  • Decisions: scope changes, consequential effects and unresolved questions.
  • Inbox: completion, failure, blockers and produced documents.
  • Dashboard: live agents and tasks from the same run records.
  • Stop team: stop new dispatch and request cancellation of descendants.
  • Artifacts and Usage: producer history and measured consumption.

Durability and migration

Keep current definitions and solo tasks. Add immutable revisions and indexed run records beside the existing store. Use a durable outbox and preallocated task UUID when creating children across the separate task and control databases. Restart reconciliation must not create duplicate work or replay uncertain external effects.

Harness integration and enforcement

Each agent has separate Harness, Model and Environment controls. Teams may mix Claude Code, Codex, OpenCode, Nebius and the other existing harness choices. Starting with native Nebius validates the coordinator; subsequent adapters enable mixed-harness execution.

Each adapter reports the capabilities it actually supports. Installation, authentication and team readiness are checked on the chosen host. A missing permission or isolation capability blocks that configuration. A prompt or Git worktree alone cannot enforce machine access. Local fallback preserves the selected harness/model; a missing local installation becomes a setup blocker rather than a silent substitution.

Resource grants and handoffs

Access is the intersection of profile, team, project, parent assignment and task authorization. Children cannot broaden it. Give each child its assignment and bounded relevant context; keep credentials in the vault or connector. Connected accounts require exact app/action grants before execution.

Parallel coding and selected environment

Begin with parallel readers and serialized writers. Then use isolated worktrees, explicit base snapshots and an integration workspace for patches. Each agent uses the Local or Nebius sandbox environment selected at creation; there is no automatic environment mode. Sandbox failures fall back locally when tools, inputs, resources and grants are compatible. Interrupted remote jobs must be reconciled before retry to avoid duplicate effects. The current ConTree command adapter is not yet a full remote agent host.

Implementation checkpoints

  1. Durable foundation: revisions, work graph, grants, attempts, claims and child-task outbox.
  2. Native delegation: lead → manager → specialist; bounded handoffs, reviews, results, stop and restart.
  3. Visible activity: hierarchy/roster, task links, decisions and consistent counts; cached native rendering.
  4. Mixed harnesses: validated external adapters and isolated patch integration.
  5. Cloud targets: selected sandbox execution, transfers, lifecycle confirmation and safe local fallback.

First release check: a three-level local team produces a document, opens a real user decision, and recovers without duplicated child work. Live provider and visual review remain separate acceptance checks.

Your confirmed defaults

Autonomy

The lead plans, delegates and reviews automatically inside configured access and budget. Ordinary assignments do not need separate approval. Scope expansion and consequential effects follow the user decision policy.

Choose harness for each agent

Every agent, including the lead, selects its own harness and supported model. Harness choice and execution environment are separate. Mixed-harness teams are supported by the planned coordinator.

Choose environment when creating the agent

Local runs the agent on your machine. Nebius sandbox runs it on the configured sandbox and falls back locally if sandbox execution fails. There is no Auto environment option; workload classification does not change your selection.

Fallback preserves the harness, model and grants, and checks local tools, inputs and hardware. An interrupted remote job must be confirmed stopped or reconciled before local retry. Show Local (fallback) and the reason in task activity. Deployments and publishing still follow the approval policy.
